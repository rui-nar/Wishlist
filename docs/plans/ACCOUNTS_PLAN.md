# Accounts — Google sign-in, sessions, sign-out and deletion

## Problem

Every feature of the first release belongs to someone: lists to their owners,
reservations and comments to invitees. Nothing can be built until a person can
sign in and the server knows, on every request, who is asking. The owner has
asked for a first deployable version with Google sign-in; Apple (required on
iOS) and email-and-password (`docs/NEEDS.md` Constraints) follow in a later
plan, on the same account and session model.

This plan also writes the first migration after the baseline. A deferred review
finding (R2-2, `docs/reviews/DEVOPS_FOUNDATION_PLAN.md`) must be fixed before
that happens: an image older than the database's Alembic revision crash-loops
on start, so rolling PROD back across this release would take it down.

## Decisions

- **D1 — Google first, one account per Google identity.** An account is
  found by Google's `sub` claim, never by email: an email can change owner or
  be shared, and linking by email would let whoever controls an address take
  over an account. Email and display name are copied from the token at each
  sign-in, for display only. Apple and email-and-password are a later plan;
  they add identity rows, not a new user table (D3).
- **D2 — The server verifies Google's ID token.** `POST /api/auth/google`
  takes the ID token the client obtained and verifies it with `google-auth`
  (`id_token.verify_oauth2_token`): signature, issuer, expiry, and audience
  equal to one of `GOOGLE_CLIENT_IDS` (comma-separated: the web client ID,
  which Android also uses as its server client ID, and later the iOS one).
  `email_verified` must be true. A 10-second clock skew is tolerated
  (TraxJourney's reason, `api/auth.py`). A failure answers 401 with a fixed
  body and logs only the exception class and a mapped reason, never any part
  of the token or the exception text (TraxJourney #510). When
  `GOOGLE_CLIENT_IDS` is empty the endpoint answers 503 "Google sign-in is not
  configured". Rules out the authorization-code flow: there is no Google API
  to call on the user's behalf, so an ID token is all the server needs.
- **D3 — Schema.** Primary keys are UUIDs (v4, generated by the server), so no
  identifier reveals how many users, lists or gifts exist.
  - `users`: `id`, `email`, `display_name`, `created_at`.
  - `user_identities`: `id`, `user_id` (FK, `ON DELETE CASCADE`),
    `provider` (`google`), `subject`, `created_at`; unique
    (`provider`, `subject`). A separate table so Apple and email-and-password
    attach to the same user later without a migration of `users`.
  - `sessions`: `id`, `user_id` (FK, cascade), `token_hash` (unique),
    `created_at`, `last_used_at`, `expires_at`.
- **D4 — Opaque sessions, stored hashed.** Sign-in returns a random token
  (`secrets.token_urlsafe(32)`); the database stores only its SHA-256. Every
  authenticated request sends `Authorization: Bearer <token>`. A session
  expires 90 days after its last use: `last_used_at` and `expires_at` move
  forward at most once per hour, so a busy client does not write on every
  request. Sign-out deletes the session; account deletion deletes them all.
  Rules out JWTs: they cannot be revoked before they expire, and deletion and
  sign-out must take effect at once.
- **D5 — One dependency decides who is asking.** `current_user` in
  `server/app/accounts/deps.py` reads the bearer token, finds the session,
  refuses it when missing, unknown or expired (401 with
  `WWW-Authenticate: Bearer`, the same body in each case, so the response does
  not say which), and returns the user. Every later endpoint that needs a user
  depends on it; none reads the header itself.
- **D6 — Runtime client configuration.** `GET /api/config` returns
  `{"google_client_id": "<web client ID or null>"}`. The web build and the
  mobile apps read it at start, so one image serves VAL and PROD with
  different `.env` values and no client rebuild. Rules out baking the client
  ID into the build with `--dart-define`: the `validation` image would then
  carry VAL's ID into PROD.
- **D7 — Endpoints.**

  | Method and path | Auth | Answer |
  |---|---|---|
  | `GET /api/config` | none | `{"google_client_id": ...}` |
  | `POST /api/auth/google` `{"id_token": "..."}` | none | 200 `{"token": "...", "user": {"id", "email", "display_name"}}` |
  | `POST /api/auth/sign-out` | bearer | 204, the session is deleted |
  | `GET /api/me` | bearer | 200 `{"id", "email", "display_name"}` |
  | `DELETE /api/me` | bearer | 204, the user and everything that cascades from them are deleted |

  Request bodies have size limits (`id_token` at most 4 KiB).
- **D8 — Account deletion now, extended by each later plan.** `DELETE
  /api/me` deletes the user row; foreign keys cascade to identities and
  sessions. Each later plan that adds data owned by or about a user states how
  deletion treats it, following `docs/NEEDS.md` ("Deleting an account"), and
  adds a test. A user who signs in again with the same Google account after
  deleting gets a new, empty account.
- **D9 — Server layout per feature.** `server/app/accounts/` holds
  `models.py`, `schemas.py`, `google.py` (token verification, injectable for
  tests), `sessions.py`, `deps.py` and `router.py`, included by
  `create_app`. Later features follow the same shape (`server/app/lists/`, …).
  A request-scoped SQLAlchemy session comes from a `db_session` dependency in
  `server/app/db.py`, using `app.state.session_factory`: one unit of work per
  request, committed when the request succeeds, rolled back when it raises.
- **D10 — Client: go_router and provider, as in TraxJourney.**
  - `go_router` with a redirect guard: a signed-out user is sent to
    `/sign-in?from=<location>` and returned to `<location>` after signing in.
    A later plan's share links (`/join/<token>`) depend on this return.
  - `provider` with an `AuthController` (`ChangeNotifier`): signed out,
    signing in, signed in (with the user), and an error state.
  - An `ApiClient` wrapping `package:http`: adds the bearer token, maps a 401
    on any call to "signed out" (the session expired or was revoked).
  - The token is kept in `flutter_secure_storage` on Android and iOS, and in
    `shared_preferences` (the browser's local storage) on the web. On the web,
    any script running in the page could read it; the page loads no
    third-party script except Google's, and only on the sign-in screen (D11).
  - Screens: sign-in (the Google button and the app name), home (a
    placeholder until the lists plan: "Signed in as <name>"), account (name,
    email, sign out, delete account with a confirmation dialog), and the
    existing version screen, reachable from the account screen.
- **D11 — Google's script loads only on the sign-in screen.** The client
  vendors TraxJourney's patched `google_sign_in_web` (BSD-3-Clause, with its
  README explaining the patch) and calls `GoogleSignIn.instance.initialize`
  only from the sign-in screen. A visitor who opens a share link and never
  reaches sign-in sends nothing to Google. Rules out upstream
  `google_sign_in_web`, which loads Google's script on every page at start.
- **D12 — Platforms for this plan.** Sign-in is verified end to end on the
  web (DEV, VAL). Android is built and configured (server client ID from
  `/api/config`); signing in on a device needs the owner's Android OAuth
  client registered with the app's package name and signing key's SHA-1,
  listed in the runbook. iOS is left for the plan that adds Apple sign-in,
  once the bundle ID is chosen (an open decision of the DevOps plan).
- **D13 — Fix R2-2: an image starts against a newer database.** The
  entrypoint runs `python -m app.migrate` instead of `alembic upgrade head`.
  It reads the database's current revision:
  - none, or a revision this image's scripts know → `upgrade head`, as
    before;
  - a revision this image does not know (the database is ahead: a rollback,
    or VAL seeded from a newer PROD) → logs one warning naming both
    revisions and starts without migrating. D15 of the DevOps plan (every
    migration keeps the previous release working) is what makes this safe.

  The runbook's Rollback and Seeding sections drop the "do not roll back
  across a migration" restriction and keep the rule that a release breaking
  D15 says so in its plan. Rules out downgrade scripts: they would run in the
  older image, which does not have them.

## Review envelope

REVIEW.md defaults apply, with these additions:

- **New external service: Google.** Google's token endpoint and keys
  (fetched and cached by `google-auth`) are untrusted input (E2): a token
  is accepted only after full verification. Google being unreachable makes
  sign-in fail with a 503-class answer; already signed-in users are
  unaffected (their sessions are ours).
- **New trust boundary: the bearer token.** Anyone holding a token is that
  user until it expires or is revoked. Tokens are stored hashed; they never
  appear in logs, URLs or error bodies.
- **Web token storage.** The token sits in the browser's local storage
  (D10). An XSS in the web client would expose it; the client renders no
  HTML from user data and loads no third-party script outside the sign-in
  screen. HttpOnly cookies are ruled out for now because DEV's client is
  cross-origin and the mobile apps use the same bearer scheme.
- **Concurrency.** Two first sign-ins of the same Google account at the same
  moment (two tabs) must produce one user: the unique (`provider`, `subject`)
  constraint decides, and the loser re-reads the winner's user.

## Boundaries crossed

- **Schema (F4):** the first tables (`users`, `user_identities`,
  `sessions`) and their migration. UUID keys and the identities table are
  chosen now because changing either later means rewriting every foreign key.
- **API contract (F4):** the five endpoints of D7 become what shipped clients
  call. Their shapes are kept; additions only.
- **Stored data:** personal data (email, display name) for the first time.
  Deletion is complete from day one (D8).
- **Rollback (R2-2):** after this plan, rolling back across a migration is
  allowed (D13).
- **Deployment configuration:** `GOOGLE_CLIENT_IDS` joins the `.env` files of
  DEV, VAL and PROD.

## Conventions

- No token, ID token, or `Authorization` header value appears in any log
  line, error body or exception message the server emits. A test proves it
  for the Google endpoint and for `current_user`.
- Every endpoint other than `/api/version`, `/api/health`, `/api/config` and
  `/api/auth/google` depends on `current_user`.
- Every user-visible client string is in both ARB files
  (`docs/DESIGN.md`).
- The server tests replace Google verification with a fake through
  dependency injection; no test calls Google.

## Definition of done

- In DEV with a Google web client ID in `.env`, the owner signs in with
  Google in Chrome, reloads and is still signed in, signs out, signs in again
  and lands on the page they were sent from.
- Deleting the account removes every row about the user; signing in again
  starts a new account.
- No log line contains a token or an ID token (tests).
- `GET /api/config` on VAL returns VAL's client ID; sign-in works on VAL once
  its origin is added to the OAuth client.
- An image that has `app.migrate` but not the database's latest revision
  starts, logs the warning and serves (`test_migrate.py`); the runbook allows
  rollback across a migration from this release on. Rolling back to an image
  older than this plan still crash-loops against a migrated database: the
